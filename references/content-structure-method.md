# 内容骨架：先读懂材料，再分页

本文件是“读材料、提炼内容、决定哪些上屏”的唯一定义处。空间定位图怎么写见 [visual-director-method.md](visual-director-method.md)；需求确认与状态记录见 [intake-and-state.md](intake-and-state.md)；门禁见 [workflow-gates.md](workflow-gates.md)。

页面出问题，常常不是画得不好，而是内容没对上。先分好页、再回原文找句子，结果是：成节的内容被悄悄舍掉，开场的内容排进了第一章，一页只剩一句漂亮话。

所以顺序固定：**读完材料 → 写内容骨架 → 给用户看 → 定页数 → 写文案稿给用户确认 → 再做页面**。骨架写在 deck 工作区的 `content-map.md`，格式见第 8 节；文案稿写在 `page-copy.md`，见第 10 节。

## 1. 先判断类型

类型决定屏幕上放什么，写在骨架第一行。

| | 知识型 | 演讲型 |
|---|---|---|
| 典型材料 | 培训课件、课程、方法讲解、操作指南 | 分享、发布、路演、致辞 |
| 讲者的目的 | 听众学会并照着做，课后还会翻回来看 | 听众记住一个观点，被打动，做一个决定 |
| 屏幕承担什么 | 知识本身：框架、步骤、判断标准 | 一个观点或一个画面，其余靠讲 |
| 一页放什么 | 一个知识点的完整结构 | 一个观点 |
| 图是什么 | 这一页的逻辑：流程、矩阵、对比、层级 | 意象、场景、情绪 |
| 怎么取舍 | 框架里的节点不能丢，细节可以合并或口述 | 只留主线，可以大胆舍 |
| 引语和金句 | 默认不上屏，用户要留才留 | 可以独占一页当高潮，在文案稿里标出来 |

- 判断线索：材料里有课程目标、练习、工具表、成体系的步骤，是知识型；第一人称的经历、故事、号召，是演讲型。
- 汇报和方案这类“让听众看懂并做决定”的材料按知识型处理：结论、依据和数据要在屏幕上。
- 一套里可以有演讲型的开场和知识型的主体，类型写主体的。拿不准就把判断和理由给用户看，由用户定。
- 把知识型做成演讲型，是最常见的错位：每页一幅画加一句口号，知识本身没上屏。

## 2. 写主线

用一两句话写清：讲者从头到尾在讲什么，各部分分别回答什么问题，前后是什么关系（总分、并列、递进、因果）。写不出主线，说明材料还没读懂，不往下走。

## 3. 逐节写三件事

每一节写三项，另有两项按需写。

- **讲者要讲什么**：一两句话，是讲者的主张，不是小节标题，也不是摘抄的一句话。
- **靠什么讲清楚**：这一节的讲解结构，写出具体内容：几个要点分别是什么，步骤的先后，对比的两边，用了什么例子和数据。页面的主体内容从这里来。
- **原文依据**：原文里的原句，用“”引出，可以写多句。脚本会到原文里逐字核对，忽略空白和换行。自己的概括不能放进引号。
- **待确认**（按需）：原文没写明、靠推断补上的地方，比如一张图里的词各属于哪一类。明说是推断，上屏前问用户。
- **不上屏**（按需）：这一节不放进页面时写理由，见第 5 节。

提炼要贴合原文：

- 强度不加码。原文说“可能”“往往”，不写成“一定”“都”。
- 范围不扩大，不替讲者下原文没有的结论，不补原文没有的例子和数据。
- 拿不准一句话是不是讲者的本意，回原文找依据；找不到就写成待确认。

节怎么切：

- 跟原文自己的标题和段落功能走。部分（`###`）用原文的章名，目录之外的开场和收尾单独成一个部分。
- 一节只有一个主张。原文一页讲了两件事，就切成两节。
- 思考题、练习、延伸阅读、工具表也是节，把类型写清楚。它们常常不上屏，但要列出来。

## 4. 引语和金句默认不上屏

- 知识型里，引语、金句、总结句和人物署名默认不上屏：屏幕留给这一节的知识本身。讲者可以口述；骨架里照常记在“原文依据”里。
- 用户明确要留某一句时才上屏，在文案稿里标“引语：用户的要求”。它留在原文所在的那一节，起它在原文里的作用（小结、佐证或引子），不顶替这一页的主体。
- 演讲型可以让一句话独占一页当高潮，同样在文案稿里标成引语，让用户一眼看到。
- 原文没有的总结句、口号不加。确实需要新增的字（序号、导航、单位）在文案稿里标“新增：理由”。
- 标题说这一页讲什么，不拿别的节里的句子当标题。
- 知识型里，只有标题加一句话的内容页是口号页，脚本会提醒。
- 确实要把一句话挪到别处，比如结尾回扣，用回顾页，或在 `[内容来源]` 里写“移动：理由”。

## 5. 页数从骨架得出

骨架写完才谈页数。总页数 = 结构页（封面、目录、章节页、结尾）+ 内容页。

- 给用户两到三档，每档写清舍什么：完整（每节一页）、标准（同级的小节合并，练习与延伸阅读改为讲师口述或发讲义）、精简（每章只留框架页）。
- 用户已经给了页数，照样先写骨架。装不下时在①说明“这个页数要舍掉这几节”，请用户选加页还是确认舍弃。不自己悄悄舍。
- 知识型的保留顺序：框架总览 → 框架里的每个节点 → 数据 → 例子、练习、延伸材料。引语默认由讲者口述。
- 图文占比的建议跟类型走：演讲型 80/20，知识型 70/30 上下。用户要更高的视觉占比，靠加页容纳内容，不删知识点。知识型的图画的是知识结构本身，所以仍然可以图为主。
- 定下档位后，不上屏的节在骨架里写“不上屏：理由”，理由里写明是用户确认的还是口述即可。

## 6. 一页对一个节点

方案里每一页写一行 `[内容来源]`，放在 `[空间定位图]` 之前：

```markdown
**[内容来源]**：封面
**[内容来源]**：目录
**[内容来源]**：章节页 C
**[内容来源]**：C2
**[内容来源]**：C3+C4
**[内容来源]**：回顾 C
**[内容来源]**：回顾 全篇
**[内容来源]**：结尾
**[内容来源]**：B4；移动：结尾要回扣这一句
```

- 一页的内容来自同一个节点。合并只合并同一部分里的同级节点，用 `+` 连接。一个节点内容多，可以拆成连续两页，两页写同一个编号。
- 标题和内容同源：标题用这个节点自己的标题或结论。
- 页面不跨章：开场的内容排在第一张章节页之前，每个部分的页连在一起。
- 顺序跟原文。确实要调整，在后面写“；移动：理由”。
- 有“总”才有“分”：一个部分内部有结构（几步、几个要素）时，先有一页总览，通常就是原文的总览节；分页上用小导航标出当前位置。
- 目录和章节页用原文的章名，不改写。
- 知识型的图承载逻辑：并列用并排或矩阵，步骤用路线，对比用左右对照，层级用剖面或阶梯。选定的风格是这张结构图的外观，不能换成“给一句口号配个场景”。

## 7. 覆盖表

拆分时脚本生成 `coverage.md`：左边是原文结构，右边是页码和处理方式（上屏、与谁合并、不上屏及理由）。④展示大纲时把它一起给用户看，用户能一眼核对有没有丢、有没有放错地方。

## 8. 文件格式

```markdown
# 内容骨架 — 《材料名》

- 类型：知识型
- 原文：source/讲义.md
- 主线：新手要完成从“凭感觉冲”到“按方案冲”的转变：先认识豆子和器具，再学冲煮方案。

### A 开场
#### A1 咖啡豆与 80%
- 讲者要讲什么：一杯咖啡的味道大部分由豆子决定，所以先学会选豆和看烘焙日期。
- 靠什么讲清楚：一句引语，一张 80% 对“其他”的占比图。
- 原文依据：“一杯好咖啡的味道”“80%来自咖啡豆”

### B 豆子与器具
#### B4 区分风味缺陷与冲煮参数
- 讲者要讲什么：喝到不好的味道时，先判断是哪个参数出了问题，再只调这一个参数。
- 靠什么讲清楚：三个概念：过萃、欠萃、通道效应，各一句定义。
- 原文依据：“每个风味缺陷的背后，都对应着一个冲煮参数”
- 待确认：三个概念在图里的位置关系，原文没有写明。
#### B6 思考题
- 讲者要讲什么：请学员回想最近一杯咖啡的问题出在哪。
- 靠什么讲清楚：三个提问。
- 原文依据：“你上一杯咖啡哪里不对？”
- 不上屏：讲师口述（用户确认按标准档）
```

- `- 类型：` 写知识型或演讲型；`- 主线：` 必填。
- `- 原文：` 写素材的文本文件，相对骨架文件所在目录，多个用分号隔开；不写时用 `deck-state.json` 里登记的素材。素材是 PDF、Word 或图片时，把读到的文字另存为 `.md` 或 `.txt` 再写在这里。
- 部分写成 `### 字母 原文章名`，节点写成 `#### 字母数字 小节名`，节点的字母和所在部分一致。
- 类型、主线、原文这三行写在第一个部分之前。说明文字可以随意加，脚本只读上面这些行。

## 9. 检查

```bash
python3 "{SKILL_DIR}/scripts/content_map.py" check --map content-map.md --state deck-state.json
python3 "{SKILL_DIR}/scripts/content_map.py" check --map content-map.md --state deck-state.json --plans design-plans.md --coverage coverage.md
```

第一条检查骨架本身：类型和主线有没有写，每节三项是否齐全，每句原文依据能不能在原文里逐字找到。通过后才能用 `deck_state.py artifact content_map content-map.md` 登记，登记后才能确认需求。

第二条检查方案和骨架是否对位，`extract_briefs.py` 拆分时也会做同样的检查，不通过就不拆分：

- 有没有页没写 `[内容来源]`，或指向不存在的节点；
- 有没有节点既没上屏，也没写“不上屏：理由”；
- 同一部分的页是否连在一起，章节页是否排在这一部分最前面；
- 页的顺序是否跟原文一致（写了“移动：理由”的除外）；
- 目录和章节页上的字是否包含原文的章名。

另有两类提醒，不拦截：知识型里只有一两处文字的内容页；上屏的节点里有待确认的推断。

脚本只查结构和引文。主张提炼得对不对、标题和内容是否同源、图有没有承载这一节的逻辑，要靠写的人自己核对，并由用户从骨架和覆盖表判断。

## 10. 文案稿：上屏的每一行先给用户确认

骨架说的是每一节讲什么，不是屏幕上写哪些字。页数确认后、找灵感和做设计之前，把全篇要上屏的文字写成一份文档 `page-copy.md`，一次给用户看、确认一次（不是一页一页问）。在这里改字不花钱；等图出来再改，每页都要重画。

```markdown
# 文案稿 — 《材料名》

## 第1页
- 内容来源：封面
- 上屏：手冲咖啡入门｜压缩

## 第3页
- 内容来源：A1
- 上屏：豆子决定大半味道｜压缩
- 上屏：80%来自咖啡豆｜原文
- 上屏：01｜新增：步骤序号
```

- 每页一个 `## 第N页`，从第 1 页连续排到已确认的页数。`内容来源` 的写法同第 6 节，方案里每页的 `[内容来源]` 要和它一致。
- 每行一条上屏文字，`｜` 后面标出处：
  - `原文`：照抄原文的句子或词，脚本到原文里逐字核对。
  - `压缩`：这一节自己的内容，缩短或改写成标题、标签。不加码、不扩大范围（第 3 节）。
  - `新增：理由`：原文没有的字，比如序号、导航、单位，必须写理由。总结句、口号、金句不是必要的新增，不加。
  - `引语：理由`：引语、金句和人物署名，逐字照抄。知识型默认不上屏，用户要留才写，理由写用户的要求；演讲型可以用，也要标出来。
- 每页第一行是标题。用户选了统一版式时，同类页的标题字数现在就写齐（六个字以内每页相同，更长的最多差 2 个字），之后用字号锁时不用回头改已确认的字；选了自由构图不限字数，标题按意思写。
- 上屏文字里不用分号（方案的可见文字清单用分号分隔字段）。
- 知识型的内容页写出这一节“靠什么讲清楚”的内容，不能只剩标题加一句话。

```bash
python3 "{SKILL_DIR}/scripts/page_copy.py" check --copy page-copy.md --map content-map.md --state deck-state.json
python3 "{SKILL_DIR}/scripts/page_copy.py" check --copy page-copy.md --map content-map.md --state deck-state.json --plans design-plans.md
```

第一条检查文案稿：格式和出处、页数、原文与引语能不能在原文里逐字找到，并按第 9 节的规则核对与骨架是否对位（有没有悄悄舍掉的节、放错章的页）。通过后用 `deck_state.py artifact page_copy page-copy.md` 登记。给用户看时把整份文案稿给全，“新增”和“引语”单独列出来；用户确认后 `decide copy --quote`。

第二条检查方案是否只显示确认过的字，`extract_briefs.py` 拆分时也会做：某页的可见文字清单比文案稿多一行、少一行，或 `[内容来源]` 不同，拆分都会失败。

确认之后要改上屏的字：先改 `page-copy.md`，把改动给用户看，重新确认，再改方案。文案稿在确认后改过而没有重新确认，拆分和生图都会被门禁拦住。用户说“直接做”并授权了文案（`delegate --scopes copy`）时免去确认，文案稿照样要写、照样检查。

脚本查不了措辞好不好、压缩得对不对，这要用户读文案稿判断。

## 没有原文时

用户只给主题或口头要点时，骨架照样写，第一行之后写 `- 原文：无`。这时没有引文可核对，每一节的内容都来自用户的原话或自己的拟稿：用户说过的照实写，自己拟的标成待确认，在①请用户逐节确认。不凭主题编造事实、数据和经历。
